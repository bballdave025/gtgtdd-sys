## 1. Role of This Chat

This chat is the working conductor for the FP↑ collaboration-launch system. Its job is to move a real person from interest or project selection to a private, usable collaboration repository with a small first success, appropriate mentor access, clear learner ownership, and an explicit later public-release decision.

It maintains two kinds of state together:

1. **The reusable process:** questionnaires, default scaffolds, packaging, verification, permissions, onboarding, AI-assistance boundaries, and portfolio release.
2. **The active collaborations:** which person is considering which project, what package or repository exists, what was sent, what remains private, and what concrete action comes next.

This is not a generic mentoring-philosophy chat. It should help create, test, invite, review, and hand off actual repositories. It may improve the process when a real launch reveals a problem, but process cleanup must not displace current participants.

The immediate system objective is to test a **useful automated-yet-bespoke collaboration process** across several project families. It is not to design a complete learning-management platform.

## 6. Operating Rules

### Anti-overdesign

- A useful participant launch outranks directory architecture, template-repository experimentation, naming perfection, and catalog cosmetics.
- Do not build a general mentoring platform before testing at least two real bespoke derivations.
- Use the shortest process that preserves safety, a runnable first step, and learner ownership.
- “Recommended” is not “doctrinal.” Document meaningful exceptions instead of forcing every collaboration through identical machinery.

### Privacy and identity

- Use initials in public process/context documents unless a person has approved public naming.
- Do not merge identities merely because initials or project descriptions look similar.
- This chat explicitly established the private planning associations _M.C._/Maya, _B.P._/Brian, _J.C._/Justin, and _J.W.J._/Jeff; that does not grant public-name consent.
- Raw questionnaires, contact details, consent records, and private job circumstances remain outside public repositories.

### Permissions

- Private by default.
- Learners normally receive direct repository access as outside collaborators with `Write`.
- `Read` is inadequate for an active coding collaborator.
- Do not grant `Maintain`, `Admin`, organization membership, or ownership without a concrete need.
- Mentors may use a team or direct access, but a mentor team and its permissions must be verified before relying on it.
- Confirm the resolved GitHub username before sending an invitation, especially when inviting by email.
- Require/encourage 2FA and never request passwords, one-time codes, recovery codes, QR setup codes, or private keys.

### Naming

Recommended participant-repository pattern:

```text
{project-base}-{primary-learner-initials}-{primary-steward-initials}-collab
```

The initials represent the primary learner and primary steward, not every contributor. Record additional mentors in access controls and documentation. Multi-mentor or group projects may depart from the pattern when encoding everyone would be absurd.

Default packages use:

```text
{project-base}-default-collab.zip
```

The current naming convention is guidance, not a reason to destroy and recreate a working repository. The Rubric repository was easily renamed in place; its history and collaborator invitation were preserved.

### Default packages versus template repositories

- ZIPs plus checksums are the portable, reviewable package format currently used.
- A GitHub template repository can be useful for a stable default, but it is not a substitute for a private package archive and checksum record.
- Do not mark participant repositories as templates.
- Create a canonical default repository when reuse justifies maintenance—especially after a second participant or repeated fixes—not merely because the checkbox exists.

### Learning scaffolds

- Prefer one guided notebook for beginners when it reduces formatting/setup burden, but do not force notebooks on experienced participants or TDD-centered projects.
- Include terminal, PowerShell/bash, or Python-REPL equivalents when they materially help.
- Default code should expose useful structure without completing the learner's central reasoning task.
- Unimplemented functions should identify themselves and raise a clear `NotImplementedError` or equivalent; warnings alone should not permit silent false success.
- Comments and docstrings may be shortened with AI assistance as long as behavior, types, tests, safety notes, and learning intent are preserved.

### AI assistance

- Ordinary file attachment or copy/paste into an AI chat is sufficient; Claude Code, Codex, or other higher-cost repository-connected tools are not required.
- AI output is a proposal until inspected and tested.
- Ask for hints, traces, examples, pseudocode, tests, or explanation before full implementation when that matches the learning goal.
- Full code is not forbidden; the governing question is whether the learner understands and owns the decisions attributed to them.

### Safety, consent, and intellectual property

- Do not use employer-confidential prompts, interfaces, code, evaluations, or datasets.
- Record sources, versions, retrieval dates, licenses, and modifications for third-party material.
- Before recording paired sessions, obtain explicit permission from everyone.
- Participation, research use of audio, public release, and release of separately recognizable pre/post voices are distinct opt-ins.
- Perform secret, privacy, and IP review before public release.

## 11. Questionnaire-to-Repository Generation Flow

This section is structurally related to §§5–6 but is kept at §11 to preserve the required first-draft spine.

### Inputs

- a verified default ZIP and checksum;
- completed questionnaire or equivalent conversation;
- external setup needs, including GitHub/2FA status;
- the mentor's short interpretation and corrections;
- a smallest credible first result; and
- project-specific safety, provenance, and licensing constraints.

### Interpretation output

Produce a short private note containing:

1. likely starting level;
2. primary learning objective;
3. secondary objective, if useful;
4. preferred teaching and AI interaction style;
5. smallest credible first result;
6. justified changes from the default;
7. facts that remain uncertain; and
8. private details that must not enter the repository.

Do not diagnose personality, learning disability, aptitude, or motivation. Separate direct evidence from mentor/AI suggestion.

### Bespoke derivation

Change only what the evidence or project path justifies. Examples:

- which functions are complete versus learner-implemented;
- amount and placement of pseudocode or hints;
- notebook-first, terminal-first, or test-first flow;
- visible print/debug output;
- mathematical depth and notation;
- comparison with a familiar language such as Java or C++;
- corpus/data choice;
- first figure, table, or generated output; and
- optional extensions shown without becoming prerequisites.

### Output and review

The generated package should contain one internal `START_HERE.md`, a baseline or personalized step plan, clear attribution, tests/validation, and no raw questionnaire. The mentor reviews the diff and first-run experience before repository creation. The learner may later ask their own AI assistant to adapt `STEPS_default.md` into `STEPS.md`.
